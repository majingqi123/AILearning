## 1. 本周目标

学完这一周，你应该能做到：

1. 讲清工作流与 Agent 的区别，以及“思考 → 行动 → 观察”循环。
2. 手写最小 Agent 循环：工具注册、参数校验、执行、回传、最大步数。
3. 为 Agent 加上拆解/重规划/反思，以及可恢复的状态与 Human-in-the-loop。
4. 实现编码工具集：读文件、写文件、编译、运行、读错误输出。
5. 在小 C++ 工程上自动修复至少 3 种常见编译错误。

## 4. 每日安排

### 周一：工作流 vs Agent，Think-Act-Observe

**学习目标**

1. 分清预定义工作流与自主 Agent。
2. 理解有效 Agent 的常见模式与设计原则。

**时间安排**：精读 50 分钟，整理笔记 25 分钟，自测 15 分钟。

**学习资源**

| 资料 | 语言 | 要求 | 看什么 |
|---|---|---|---|
| [Building effective agents](https://www.anthropic.com/research/building-effective-agents) | 英文 | 必读 | 全文 |
| W12 工具调用程序 | — | 必读 | 它还不是完整 Agent 循环 |

**动手任务**

1. 笔记画图：工作流（固定边）vs Agent（模型选下一步）。
2. 摘录 5 条你认同的设计原则（例如：先简单、工具要少而清、限制循环、保留可观测性）。
3. 用自己的话写清：一次 Agent 步里“思考、行动、观察”各对应程序里的什么。

**验收标准**

- [ ] 能向别人解释“Agent ≠ 多次 API 调用”的那点差别。
- [ ] 有原则清单，周末实现时逐条对照。

**自测题**

1. 什么任务更适合工作流而不是 Agent？
2. 为什么工具越多不一定越好？
3. 观察（Observation）如果不回传，循环会怎样？

### 周二：手写最小 Agent 循环

**学习目标**

1. 实现通用循环：模型输出 → 解析工具调用 → 校验 → 执行 → 回传 → 直到结束或达上限。
2. 把“结束”做成显式（最终答案工具或 `finish` 标志），不要靠运气停。

**时间安排**：设计 15 分钟，编码 60 分钟，笔记 15 分钟。

**学习资源**

| 资料 | 语言 | 要求 | 看什么 |
|---|---|---|---|
| W12 Function Calling 文档与代码 | — | 必读 | 工具协议 |
| Building effective agents | 英文 | 必读 | 关于简单循环的部分 |

**动手任务**

1. 工具注册表：`name → schema + handler`。
2. 实现 `run_agent(goal, max_steps)`：
   - 每步打印：选用的工具、参数、结果摘要
   - 非法参数拒绝并返回错误观察
   - 达 `max_steps` 强制停止并报告
3. 用非编码工具先测通（时间、计算器、读指定文本文件）。

**验收标准**

- [ ] 最小 Agent 能完成需要 2+ 次工具调用的任务。
- [ ] 死循环被 `max_steps` 拦住。

**自测题**

1. 参数校验应该在模型侧还是程序侧兜底？
2. 工具执行异常时，应该抛崩还是变成 Observation？
3. 为什么要记录每一步轨迹（trace）？

---

### 周三：拆解、重规划、反思

**学习目标**

1. 让 Agent 面对多步目标时先规划再执行。
2. 失败后能重规划或自我修正，而不是重复同一错误动作。

**时间安排**：读资料 20 分钟，动手 55 分钟，笔记 15 分钟。

**学习资源**

| 资料 | 语言 | 要求 | 看什么 |
|---|---|---|---|
| Building effective agents | 英文 | 必读 | routing / orchestration 相关思路 |
| [Reflexion 论文（了解）](https://arxiv.org/abs/2303.11366) | 英文 | 选读 | 摘要：语言反馈作为记忆 |

**动手任务**

1. 增加可选 `plan` 阶段：输出步骤列表（结构化 JSON）。
2. 执行中若连续两次同类失败，触发 `replan` 或 `reflect`（把失败原因写入上下文）。
3. 设计一个多步任务：例如“读取 A 文件中的表达式 → 计算 → 写入 B 文件 → 再读回校验”。
4. 对比：无规划 vs 有规划的成功率与步数。

**验收标准**

- [ ] 至少 1 个多步任务稳定完成。
- [ ] 有一次“失败 → 反思 → 改策略”的轨迹日志。

**自测题**

1. 规划过细有什么坏处？
2. 反思内容应该存短期上下文还是长期记忆？
3. 如何避免 Agent 在反思里空话连篇却不改动作？

### 周四：记忆、Checkpoint、Human-in-the-loop

**学习目标**

1. 区分短期上下文与长期记忆。
2. 实现可序列化状态，支持中断恢复。
3. 对危险操作加入人工确认。

**时间安排**：设计 20 分钟，编码 55 分钟，笔记 15 分钟。

**学习资源**

| 资料 | 语言 | 要求 | 看什么 |
|---|---|---|---|
| Building effective agents | 英文 | 必读 | 控制与人机协同相关段落 |
| W12 上下文管理笔记 | — | 必读 | 历史裁剪可复用 |

**动手任务**

1. 定义 `AgentState`：messages、计划、当前步、工作目录、轨迹、checkpoint_id。
2. 每步后写入 `checkpoints/*.json`；支持从某 checkpoint 恢复。
3. HITL：对 `write_file` / `run_command` 等危险工具，先打印计划中的动作，等用户 `y/n`（可加白名单路径自动通过）。
4. 演示：跑到一半 Ctrl+C，再从 checkpoint 继续。

**验收标准**

- [ ] 状态可恢复。
- [ ] 危险操作确认流程可用。

**自测题**

1. 为什么“长期记忆”不能等同于把所有轨迹塞回 prompt？
2. Checkpoint 最小应保存哪些字段？
3. 哪些操作可以自动、哪些必须 HITL？

### 周五：编码 Agent 工具集

**学习目标**

1. 实现读/写文件、编译、运行、读取 stderr/stdout 的工具。
2. 把工具权限限制在项目沙箱目录。

**时间安排**：编码 70 分钟，安全检查 15 分钟，笔记 10 分钟。

**学习资源**

| 资料 | 语言 | 要求 | 看什么 |
|---|---|---|---|
| W12 读文件沙箱思路 | — | 必读 | 路径约束 |
| CMake / 你的编译命令 | — | 必读 | 统一 `build` 入口 |

**动手任务**

1. 工具清单（名称可调整）：
   - `list_dir` / `read_file` / `write_file`
   - `build`（例如 `cmake --build ...`）
   - `run`（可执行文件，带超时）
   - `read_build_log`（或让 `build` 直接返回截断后的错误）
2. 硬约束：所有路径解析后必须落在 `workspace/` 内；禁止任意 shell 拼接（能参数化就参数化）。
3. 准备 3 个故意坏掉的工程快照：缺分号/未声明、类型错误、找不到头文件或链接错误等。
4. 手工调用工具，确认编译错误文本能稳定拿到。

**验收标准**

- [ ] 工具集可独立单测。
- [ ] 沙箱外路径访问被拒绝。

**自测题**

1. 为什么不直接给 Agent 一个万能 `shell`？
2. 编译日志太长时怎么截断才不丢关键错误？
3. `run` 为什么必须有超时？

### 周末：最小编码 Agent——自动修编译错误

**学习目标**

1. 串起循环 + 编码工具，自动修复编译错误。
2. 至少覆盖 3 种错误类型，留下可演示轨迹。

**时间安排**（约 3–4 小时）：联调 120 分钟，三类错误验收 40 分钟，README/复盘 30 分钟。

**学习资源**

| 资料 | 语言 | 要求 | 看什么 |
|---|---|---|---|
| 本周全部代码与原则清单 | — | 必读 | — |
| W14 代码检索（可选接入） | — | 选做 | 修错时检索 API 用法 |

**动手任务**

1. 目标输入：`workspace` 路径 + “修复到能编译通过”。
2. 循环策略建议：`build` → 读错误 → `read_file` → `write_file` → 再 `build`。
3. 成功标准：退出码 0；记录轮数与改动文件。
4. 跑通至少 3 类错误各 1 例；保存 `traces/`。
5. （可选）编译通过后再 `run`，做最小运行验证。
6. README + 更新 [进度追踪](../进度追踪.md)。

**验收标准**

- [ ] 编码 Agent 能自动修复至少 3 种常见编译错误。
- [ ] 能解释 Agent 不等于“一个提示词”或“多次 API 调用”。

## 7. 容易踩的坑

- **一上来接入复杂框架**：本周必须手写循环，框架放到 W17。
- **万能 shell**：又难控又危险，综合项目也会埋雷。

- **修错时不读文件上下文**：模型容易瞎改。
- **工作区太脏**：每个错误类型用独立副本，便于回归。
